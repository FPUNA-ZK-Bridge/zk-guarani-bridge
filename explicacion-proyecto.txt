1. QUE ES?
----------
Es un bridge de tokens cross-chain que transfiere GuaraniTokens entre dos
blockchains (L1 y L2) usando el patron lock-and-mint con verificacion de
pruebas de conocimiento cero (ZK).


2. FLUJO COMPLETO
-----------------

L1 (Hardhat/Ephemery)                    L2 (Anvil/BlockDAG)

1. Usuario aprueba tokens
2. Usuario llama lock(recipient, amount)
   -> Tokens bloqueados en Sender
   -> Emite evento Locked

              RELAYER (escucha Locked)
              |
              v
3. Consulta Beacon Node (Sync Committee)
4. Genera prueba ZK (Circom/Groth16)
5. Llama mintRemote() en Receiver ------> 6. Verifica prueba ZK on-chain
                                          7. Mintea tokens al destinatario
                                          8. Emite evento Minted


3. COMPONENTES CLAVE
--------------------

+---------------------+------------------------------------------------------+
| Componente          | Descripcion                                          |
+---------------------+------------------------------------------------------+
| Sender.sol (L1)     | Bloquea tokens, emite evento Locked                  |
| Receiver.sol (L2)   | Verifica prueba ZK + mintea tokens                   |
| Groth16Verifier.sol | Verifica pruebas Groth16 on-chain (L2)               |
| Relayer (Node.js)   | Escucha L1, genera pruebas, envia a L2               |
| generate_data/      | Obtiene datos del Beacon Node y los transforma       |
|                     | al formato Circom (Tusima/BLS)                       |
+---------------------+------------------------------------------------------+


4. CONTRATOS SOLIDITY
---------------------

a) GuaraniToken.sol
   - ERC20 con AccessControl (OpenZeppelin)
   - Roles: DEFAULT_ADMIN_ROLE, MINTER_ROLE
   - Supply inicial en L1 (1M tokens), supply 0 en L2 (se mintea via bridge)

b) Sender.sol (L1 - Lock Side)
   - lock(recipientL2, amount): bloquea tokens (requiere approval previo)
   - Almacena Lock data: {from, to, amount}
   - Emite evento Locked(id, from, to, amount)
   - Nonce incremental para cada transferencia

c) Receiver.sol (L2 - Mint Side)
   - mintRemote(id, to, amount, pA, pB, pC, pubSignals): solo el relayer
   - Verifica prueba ZK via Groth16Verifier
   - Previene replay attacks: require(!processed[id])
   - Mintea tokens al destinatario
   - Emite evento Minted(id, to, amount)

d) ReceiverV2.sol (Version alternativa con Updater)
   - Version mejorada usando contrato Updater
   - Separacion de dominio via lockKey()
   - Arquitectura para futura integracion de light-client

e) Updater.sol (MVP/Prototipo)
   - Mantiene estado aceptado de L1 en L2
   - acceptHeader(blockNumber, root): actualizar estado L1
   - acceptLock(id, to, amount): marcar lock como aceptado
   - MVP: futuras versiones verificaran headers/receipts reales

f) Groth16Verifier.sol
   - Generado automaticamente por snarkjs
   - Verifica pruebas en formato Groth16
   - Curva BN254/Alt-BN128
   - verifyProof(pA, pB, pC, pubSignals) -> bool

g) Verifier.sol
   - Stub/placeholder para futura integracion Noir/Plonk

6. RELAYER (relayer/relayer.js)
-------------------------------

Servicio autonomo Node.js que conecta las dos cadenas.

Funciones principales:
  a) Event Listening:
     - Polling HTTP o suscripcion WebSocket para eventos Locked en N1
     - Polling HTTP para eventos Minted en N2 (confirmacion)

  b) Proof Generation:
     - Consulta Beacon Node API (Sync Committee data)
     - Transforma datos al formato Circom via generate_data/transformData.js
     - Genera prueba ZK con snarkjs.groth16.fullProve()
     - Actualmente usa multiplier2 (TODO: migrar a BLS)

  c) On-Chain Execution:
     - Llama mintRemote() en Receiver con la prueba
     - Soporta gas pricing legacy y EIP-1559
     - Reintentos (3 intentos) con manejo de errores

Variables de entorno:
  RPC_URL_N1           - RPC de L1
  RPC_URL_N2           - RPC de L2
  PRIVATE_KEY_RELAYER  - Clave privada del relayer
  BEACON_NODE_URL      - Beacon node (default: localhost:5052)
  N2_GAS_LIMIT         - Gas limit opcional
  N2_GAS_PRICE_GWEI    - Gas price legacy opcional
  N2_MAX_FEE_GWEI      - EIP-1559 max fee opcional
  N2_PRIORITY_FEE_GWEI - EIP-1559 priority fee opcional

   - Output: signing_root[32], pubkeys[512][2][7], bits[512], signature G2

12. PROBLEMA
------------

El circuito real de verificacion BLS Sync Committee tiene 8 partes
(part1a-e, part2, part3a-b) y requiere recursos que tu maquina local
no puede proveer:

Metricas del servidor EPYC (AMD EPYC 9655, 32 cores, 128 GB RAM):

  Compilacion:              11m 23s
  Generacion de testigos:    1m 36s
  Trusted Setup (zkey):     39m 21s  (part2 usa 69 GB de RAM!)
  Generacion de pruebas:       26s   (con rapidsnark)
  Verificacion:                 1.2s
  Pipeline total:           53m 4s

El cuello de botella principal es la RAM:
  - part2 trusted setup: 69,355 MB (69 GB)
  - part3b trusted setup: 46,827 MB (46 GB)
  - part2 proof generation: 8,466 MB (8.5 GB)


13. DISTINCION CLAVE: SETUP vs RUNTIME
---------------------------------------

Los 53 minutos son SETUP (se hace UNA SOLA VEZ):
  - Compilacion de circuitos -> genera .wasm/.cpp y .r1cs
  - Trusted Setup (Powers of Tau + zkey) -> genera .zkey

En PRODUCCION, por cada transferencia solo se necesita:
  - Witness generation: ~1m 36s
  - Proof generation (rapidsnark): ~26s
  - TOTAL POR TRANSFER: ~2 minutos

La compilacion y el trusted setup se ejecutan una vez y los artefactos
(.zkey, .wasm, .cpp) se reutilizan indefinidamente.

+-------------------------+      +----------------------------------+
|   Tu maquina local      |      |   Servidor EPYC remoto           |
|                         |      |   (96 cores, 128 GB RAM)         |
|  - Contratos            |      |                                  |
|  - Relayer              |      |  - Circuitos compilados (.cpp)   |
|  - Frontend             |      |  - zkeys generados               |
|  - Tests                |      |  - rapidsnark instalado          |

|  Relayer:               |      |                                  |
|  1. Detecta Locked      | HTTP |  Prover Service:                 |
|  2. POST /prove --------+------+-> Recibe input.json              |
|     {input.json}        |      |   Genera witness (.wtns)         |
|  3. Recibe proof <------+------+-- Ejecuta rapidsnark             |
|  4. mintRemote()        |      |   Retorna proof.json             |
+-------------------------+      +----------------------------------+


15. PROBLEMA DEL TIMEOUT HTTP
-------------------------------

La generacion de pruebas toma ~2 minutos. Un request HTTP sincrono
fallaria porque el timeout por defecto es 30-60 segundos. Proxies,
firewalls y balanceadores tambien cortan conexiones idle.

Solucion: patron ASINCRONO con polling (job queue).

El servidor recibe el trabajo, devuelve un jobId inmediatamente (<1s),
y el relayer hace polling cada 5 segundos hasta que el resultado este listo.

Ventajas:
  - No depende de mantener una conexion TCP viva 2+ minutos
  - Si el relayer se reinicia, puede retomar consultando el jobId
  - Se puede ver el estado del proving en cualquier momento
  - Funciona bien con proxies/firewalls que cortan conexiones idle

PASO 1: SERVICIO DE PROVING ASINCRONO EN SERVIDOR REMOTO
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Crear un servicio HTTP en el servidor EPYC con patron async job queue.

Archivo: prover-service/server.js (en el servidor EPYC)

    import express from 'express';
    import crypto from 'crypto';
    import { execSync } from 'child_process';
    import fs from 'fs';

    const app = express();
    app.use(express.json({ limit: '50mb' }));

    // Almacen de jobs en memoria
    const jobs = new Map();

    // POST /prove - Recibe trabajo, responde inmediato con jobId
    app.post('/prove', (req, res) => {
      const { input, part } = req.body;
      const jobId = crypto.randomUUID();

      jobs.set(jobId, { status: 'processing', part, createdAt: Date.now() });

      // Ejecutar en background (no bloquea el response)
      runProof(input, part, jobId);

      // Responde en <1 segundo con el jobId
      res.json({ jobId, status: 'processing' });
    });

    // GET /prove/:jobId - Consultar estado del job
    app.get('/prove/:jobId', (req, res) => {
      const job = jobs.get(req.params.jobId);
      if (!job) return res.status(404).json({ error: 'job not found' });
      res.json(job);
    });

    // Funcion que ejecuta el proving en background
    async function runProof(input, part, jobId) {
      try {
        // 1. Escribir input
        fs.writeFileSync(`/tmp/input_${part}.json`, JSON.stringify(input));

        // 2. Generar witness (usando el witness generator C++ compilado)
        execSync(
          `./circom/${part}_cpp/${part} /tmp/input_${part}.json /tmp/witness_${part}.wtns`,
          { timeout: 300_000 } // 5 min max para witness
        );

        // 3. Generar prueba con rapidsnark
        execSync(
          `rapidsnark circom/${part}.zkey /tmp/witness_${part}.wtns ` +
          `/tmp/proof_${part}.json /tmp/public_${part}.json`,
          { timeout: 300_000 } // 5 min max para proving
        );

        // 4. Leer resultados
        const proof = JSON.parse(fs.readFileSync(`/tmp/proof_${part}.json`));
        const publicSignals = JSON.parse(
          fs.readFileSync(`/tmp/public_${part}.json`)
        );

        // 5. Actualizar job como completado
        jobs.set(jobId, {
          status: 'done',
          part,
          proof,
          publicSignals,
          completedAt: Date.now(),
        });

        console.log(`Job ${jobId} (${part}) completado exitosamente`);
      } catch (e) {
        jobs.set(jobId, {
          status: 'error',
          part,
          error: e.message,
          completedAt: Date.now(),
        });
        console.error(`Job ${jobId} (${part}) fallo: ${e.message}`);
      }
    }

    // Limpieza periodica: eliminar jobs viejos (>1 hora)
    setInterval(() => {
      const oneHour = 60 * 60 * 1000;
      for (const [id, job] of jobs) {
        if (job.completedAt && Date.now() - job.completedAt > oneHour) {
          jobs.delete(id);
        }
      }
    }, 60_000);

    app.listen(3001, () => console.log('Prover service (async) en puerto 3001'));


PASO 2: MODIFICAR EL RELAYER LOCAL (con polling)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Reemplazar la funcion generateProof() en relayer/relayer.js para usar
el prover remoto con patron async + polling.

    const PROVER_URL = process.env.PROVER_URL || "http://tu-servidor-epyc:3001";
    const POLL_INTERVAL_MS = 5000;  // consultar cada 5 segundos
    const POLL_TIMEOUT_MS = 600000; // timeout maximo: 10 minutos

    /**
     * Envia un job de proving al servidor remoto y espera el resultado
     * usando polling. No depende de mantener la conexion HTTP abierta.
     */
    async function proveRemote(circomInput, part) {
      // 1. Enviar job - respuesta inmediata con jobId
      const submitResp = await fetch(`${PROVER_URL}/prove`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ input: circomInput, part }),
      });
      if (!submitResp.ok) {
        throw new Error(`Prover rechazo job ${part}: ${submitResp.status}`);
      }
      const { jobId } = await submitResp.json();
      console.log(`  Job enviado: ${part} -> jobId=${jobId}`);

      // 2. Polling hasta que termine o falle
      const startTime = Date.now();
      while (true) {
        await new Promise(r => setTimeout(r, POLL_INTERVAL_MS));

        // Verificar timeout total
        if (Date.now() - startTime > POLL_TIMEOUT_MS) {
          throw new Error(`Timeout esperando proof ${part} (jobId=${jobId})`);
        }

        const pollResp = await fetch(`${PROVER_URL}/prove/${jobId}`);
        if (!pollResp.ok) {
          throw new Error(`Error consultando job ${jobId}: ${pollResp.status}`);
        }
        const job = await pollResp.json();

        if (job.status === 'done') {
          console.log(`  Job completado: ${part}`);
          return { proof: job.proof, publicSignals: job.publicSignals };
        }

        if (job.status === 'error') {
          throw new Error(`Prover fallo en ${part}: ${job.error}`);
        }

        // status === 'processing' -> seguir esperando
        const elapsed = Math.round((Date.now() - startTime) / 1000);
        console.log(`  Esperando ${part}... (${elapsed}s)`);
      }
    }

    async function generateProof(id, amount) {
      console.log(`Generando prueba ZK remota para id=${id}...`);

      // 1. Construir input del circuito desde beacon node
      const circomInput = await buildCircomInput();

      // 2. Enviar a prover remoto para cada parte (con polling)
      const proofs = {};
      const parts = ['part1a','part1b','part1c','part1d','part1e',
                     'part2','part3a','part3b'];

      for (const part of parts) {
        proofs[part] = await proveRemote(circomInput, part);
      }

      // 3. Tomar la prueba final y formatear para Solidity
      const { proof, publicSignals } = proofs.part3b; // prueba agregada final

      const pA = [proof.pi_a[0], proof.pi_a[1]];
      const pB = [
        [proof.pi_b[0][1], proof.pi_b[0][0]],
        [proof.pi_b[1][1], proof.pi_b[1][0]],
      ];
      const pC = [proof.pi_c[0], proof.pi_c[1]];

      return { pA, pB, pC, pubSignals: publicSignals.map(String) };
    }

NOTA SOBRE PARALELIZACION: Si las partes son independientes, se pueden
enviar todas en paralelo con Promise.all() para reducir el tiempo total:

    const results = await Promise.all(
      parts.map(part => proveRemote(circomInput, part))
    );

Esto haria que el tiempo total sea el de la parte mas lenta (~37s para
part2) en lugar de la suma de todas (~2 min secuencial).

17. CONSIDERACIONES IMPORTANTES
---------------------------------

a) Compilacion y Trusted Setup son ONE-TIME:
   Solo se ejecutan una vez. Los artefactos (.zkey, .wasm, .cpp)
   se reutilizan para siempre. Los 53 minutos NO se repiten por transfer.

b) Tiempo por transferencia en produccion:
   Witness generation: ~1m 36s
   Proof generation (rapidsnark): ~26s
   Total: ~2 minutos por transfer

c) El Groth16Verifier.sol DEBE coincidir con el circuito:
   Se genera a partir del .zkey del circuito real, NO del multiplier2.
   Si hay mismatch, todas las pruebas seran rechazadas on-chain.

d) Seguridad del prover remoto:
   - Agregar autenticacion (API key o mTLS)
   - No exponer el servicio a internet sin proteccion
   - Considerar VPN o tunnel SSH

e) Paralelizacion de partes:
   Si las 8 partes del circuito son independientes entre si,
   se pueden generar en paralelo en el servidor EPYC, reduciendo
   el tiempo total de proving significativamente.

f) Alternativa: SSH directo:
   En lugar de un servicio HTTP, el relayer podria ejecutar
   los comandos directamente via SSH al servidor EPYC.

    const { execSync } = require('child_process');
    execSync(`ssh epyc "cd /path/to/circom && ./prove.sh"`);
